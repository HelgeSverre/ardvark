**Goal:** Update ardvark from the v0.9 catalog-centric model to the final v0.91
entry-centric JSON-LD model while retaining discovery and ingestion
compatibility with existing `ai-catalog.json` publishers.

**Architecture:** Separate transport/source decoding from ARD entry
conformance. A source may be a legacy catalog manifest, the final `ard.json`
transport, a standalone entry, in-page JSON-LD, or a Registry Search
projection. Full entries are validated independently against
`ard-entry.schema.json`; source-level status is an aggregation over entry
results plus transport checks. Raw entry JSON is preserved so JSON-LD context
and namespaced extensions survive ingestion even when ardvark does not
understand them.

## Global Constraints

- Do not begin implementation until Task 0's final-spec gate is satisfied.
- `/.well-known/ard.json` and `rel="ard"` become preferred; the legacy
  `/.well-known/ai-catalog.json` path and `rel="ai-catalog"` token remain
  supported aliases.
- Never validate a Registry Search result projection as though it were a
  complete ARD entry. Draft §5.3.2 explicitly permits projections to omit
  terms, especially `representativeQueries`.
- Preserve raw entry JSON, `@context`, `@id`, and unknown/namespaced
  properties. Parsing known fields must not destroy unknown fields.
- Keep old crawled data readable. Database changes must be additive or have an
  explicit, tested migration/backfill.
- Keep invalid/nonconforming sources and entries stored with their raw bytes
  and checks; do not silently discard them.
- Continue to document every intentional leniency separately from strict
  final-schema conformance.
- Use red-first tests for each behavioral change. Run `just check` before each
  task is considered complete.
- Preserve unrelated worktree changes. The repository was already dirty when
  this plan was written.

## Normative Changes Already Clear in the Draft

These can be planned now, though exact schema details still come from the final
artifacts:

1. The ARD entry, not the hosted catalog manifest, is the conformance unit
   (draft §4 and Appendix D.1).
2. Entries are JSON-LD nodes and may carry `@context`, `@id`, and terms from
   additional namespaces (draft §§3.4, 4.1, and Appendix C).
3. `representativeQueries` is required for a complete ARD entry; 2–5 examples
   remains a recommendation (draft §4.2 and Appendix D.2).
4. The URN publisher must align with the cryptographic trust domain in
   `trustManifest.identity` (draft §4.5.1 and Appendix D.2).
5. `/.well-known/ard.json` and `rel="ard"` are the preferred discovery names;
   the former names remain aliases (draft §5.1).
6. Required web ingestion covers hosted entry sources and in-page JSON-LD
   markup (draft §5.2).
7. Unknown/additional namespace terms must remain available to discovery
   consumers rather than being dropped (draft §§3.4, 4.1, and 5.3.1).

## Final-Spec Questions That Block Exact Implementation

Record the final answer to each question in this document or a linked decision
record before implementing the affected task.

| Question | Why it matters | Current safe assumption |
|---|---|---|
| What is the JSON shape served at `/.well-known/ard.json`? | Draft §5.1 calls it a “manifest of entries,” while Appendix D.1 defines only a single entry. | Support the legacy `{specVersion, host, entries}` decoder and wait for the final transport shape before adding a new decoder. |
| What is the default namespace IRI/context? | True JSON-LD term expansion cannot be implemented without it. | Preserve context and raw terms; do not invent an IRI. |
| Is a namespace segment required in `urn:air:` identifiers? | The stated grammar includes `<namespace>`, but a Search example uses `urn:air:example.com:weather-server`. | Keep accepting publisher + terminal name until the final schema resolves it. |
| Which `trustManifest.identity` schemes assert a domain, and how is that domain extracted? | Domain comparison differs for `did:web`, HTTPS, SPIFFE, and other principals. | Do not infer a universal parser from the prose; implement the final schema/tool procedure. |
| How is “same resource” determined when `@id` is an HTTP IRI rather than the same URN as `identifier`? | Appendix C makes this a MUST but does not define an offline equivalence algorithm. | Enforce exact equality when applicable and follow final conformance-tool behavior for alternate IRIs. |
| Does an entry’s `url` retrieve the artifact or the complete ARD entry? | §4.3 calls it the artifact document; §5.3.2 says the full entry is retrievable from it. | Do not change artifact fetching until the final wording/schema clarifies this. |

## Non-goals for the v0.91 Compatibility Release

- Building an ARD Registry HTTP server. The REST-interface MUST applies to
  Agent Registries; ardvark is currently a crawler/indexer and Registry client.
- Implementing optional Explore or List endpoints as a server.
- Full cryptographic signature, attestation, DID, SPIFFE, or key-resolution
  verification unless the final conformance requirements make it mandatory
  for ardvark's advertised strict verifier. Structural/domain binding remains
  in scope.
- DNS Service Binding discovery unless the final specification makes consumer
  support normative. Documentation must not claim DNS support while it is
  absent.
- Expanding or semantically reasoning over every external JSON-LD vocabulary.
  Preservation is required; indexing/understanding every namespace is not.
